# 架构设计

这份文档说明代码为什么这样组织，以及哪些地方是刻意的取舍。目的是让你能判断后续改动该落在哪一层，也方便我们讨论还有哪些优化空间。

## 一句话概括

两个互不依赖的包，一个把美团的接口数据落成文件，一个把文件渲染成视频，中间只靠 `data/` 目录交接。

```
HAR (凭证)
  │
  ▼
┌─────────────────────────────┐
│ ridedata                    │   抓取 + 整理
│  api ─ fetch ─ bulk         │
│         └ prepare/selection │
└──────────────┬──────────────┘
               │  写 JSON / CSV
               ▼
           data/  ◄── 唯一接口
               │  读 JSON
               ▼
┌─────────────────────────────┐
│ ridevideo                   │   渲染
│  load ─ basemap ─ camera    │
│         └ frame ─ render    │
└──────────────┬──────────────┘
               ▼
          data/video-out/*.mp4
```

## 为什么是两个包而不是一个

这两半的性质完全不同：

| | ridedata | ridevideo |
|---|---|---|
| 依赖 | 只要 Python | macOS + MapKit + swiftc + ffmpeg |
| 失败代价 | 要重新请求接口，受签名有效期限制 | 本地重算，随时可重来 |
| 幂等性 | 不幂等（每次请求结果可能不同） | 幂等（同样输入必得同样输出） |
| 变更频率 | 接口变了才动 | 调画面时天天动 |

拆开的实际好处是渲染可以反复重跑而不碰接口。抓取一次要几十分钟且受凭证有效期约束，渲染改一版颜色就要重跑——这两件事必须能独立进行。

有一条测试守着这个边界（`test_pipeline_contract.py`），用 AST 检查 `ridevideo` 是否 import 了 `ridedata`。之所以查 AST 而不是文本，是因为 docstring 里提到对方的名字不该算依赖。

代价是有意接受的重复：两个包各有一份 `paths.py` 和时长格式化。如果抽成第三个共享包，就等于把三个包绑在一起发布，为省二十行不值得。有测试（`test_matches_the_data_side`）保证两份格式化输出一致。

## ridedata：四层

```
api.py          接口定义 + 凭证提取     ← 唯一碰凭证的地方
   ▲
fetch.py        单日抓取 + 字段规范化
   ▲
bulk.py         多年抓取 + 连接检测
   ▲
prepare/        selection（换筛选规则，不重抓）
```

### api.py：接口写在代码里，HAR 只给凭证

早先的设计是 `input/request.curl` 同时承载凭证、URL、请求体和 curl 参数。问题是任何一项要改都得手工重抄文件，而且凭证和接口定义混在一起，没法单独更新其中一个。

现在 URL、请求体、分页、重试、超时全在 `api.py`，HAR 只贡献 `Cookie` 和 `userid` / `yoda*` 这几个头。这样：

- 接口变更是一次代码改动，不需要用户重抓 HAR
- 凭证过期只需重抓 HAR，不需要碰代码
- 凭证提取逻辑只有一份（以前 `fetch` 和 `bulk` 各有一份 108 行的，74% 重复）

HAR 解析有个实际考虑：Cookie 常常散落在多个请求里——埋点请求带 session cookie，地图请求带设备头。所以取的是**所有请求 Cookie 的并集**，这样从普通浏览抓的 HAR 也能用，不必精确抓到那一个历史接口请求。

### 筛选规则：为什么是 YAML 而不是 CLI 参数

抓详情要按订单逐笔请求，所以得先挑日期。原来是 `--threshold-minutes` 加 `--threshold-mode {single-order,daily-total}` 两个硬编码模式，加第三种口径就得改代码，而且产出数据里只留下 `thresholdMode: single-order` 这样的字符串，事后看不出完整条件。

现在规则在 `filters.yaml`，`filters.py` 提供条件表和校验：

```yaml
rules:
  real-gps:
    description: 当天至少有一笔含真实 GPS 轨迹
    has_full_track: true
```

设计上的几个决定：

- **条件表是白名单**。未知条件名在加载时报错，不是忽略——一个拼错的条件如果静默匹配所有日期，比报错难查得多。
- **一条规则内的条件是「与」**。没做 or/not，因为目前的用例都是「与」，加布尔组合会让 YAML 变成一门小语言。真需要时可以加 `any_of:` 嵌套。
- **完整条件写进产出**。`summary.json` 里存 `filterConditions`，数据和产生它的口径绑在一起。
- **`select` 能重跑规则**。详情抓完后换口径不需要重新请求接口，旧结果归档到 `archive/<上次规则名>/` 而不是删掉，两种口径可以对照。

有个时序上的限制值得注意：`has_full_track` 这类条件依赖轨迹信息，而轨迹要抓详情才知道。所以这类规则在 `bulk` 阶段选不出日期，必须用 `select`。这个限制写在 `filters.yaml` 的注释和 `bulk.py` 的代码注释里。

### prepare/：只剩 selection

原来有三步：`selection` 挑日期、`groups` 展开连续订单组、`manifest` 出任务清单。后两步已删，原因见下一节。

连接判断的规则是「前单终点到后单起点直线距离 ≤ 500 米，且间隔在 0–2 小时内」——空间近**且**时间近才算连续。这只是候选线索，**不把直线距离当道路轨迹**，这个区分在代码注释和输出的 `note` 字段里都写明了。

连接信息保留在 `days/*.json` 里，渲染时用来决定哪两段之间标「转场」。

## 产出粒度：为什么是天

一个入选日期产出一个视频。

早先的链路是 `selection` → `groups` → 渲染每个组，也就是先把当天的骑行按连接规则切成若干「连续组」，每组一个视频。这个设计有个根本问题：
**它只导出连成组的订单，落单的直接丢掉。**

实测 49 个入选日期：

- 20 天完全没有任何组，一个视频都产不出来
- 这 20 天里有 92 分钟、84 分钟、82 分钟的长途骑行，正是最值得做视频的
- 另外 20 天有组但仍有落单，共 26 笔被丢弃
- 195 笔订单里只有 127 笔进了组

最极端的是 `2026-03-27`：当天只有 1 笔 92 分钟的骑行。它永远不可能「成组」，所以永远不会有视频——但它显然是这批数据里最该被看到的一天。

改成按天之后：

- 筛选规则挑出的单位（天）和产出单位（视频）一致，不需要中间再切一刀
- 连得上的段在片中自然接起来，连不上的标「转场」——视频侧的 `TRANSFER_KM` 逻辑本来就支持，只是之前没被用在这个场景
- 49 天 → 49 个视频，一笔骑行都不丢
- `groups/` 那层目录不再需要：它是把 `days/*.json` 的数据复制一遍，而且只复制成组的部分。`manifest` 同理，它的清单没有消费者了

代价是一天里如果有两段相距很远的骑行，它们会在同一个视频里，中间有一次转场。这比丢掉其中一段更诚实——那一天确实骑了这两段。

## ridevideo：分层渲染

```
load        读 JSON → Day/Ride，标 gps/inferred
  ▲
basemap     MapKit 快照（超采样 + 并行 + 磁盘缓存）
camera      时间轴 + 镜头裁切
  ▲
frame       Pillow 合成单帧
  ▲
render      帧序列 → ffmpeg
batch       多进程批量
```

`load` 在最底层，其他模块都依赖它，它不依赖任何人。依赖图无环。

### 几个关键设计

**超采样 + Ken Burns**。底图按 1.5 倍尺寸渲染一次，镜头推近靠裁切和缩放实现，而不是每帧重新请求快照。这让每帧从 1.5 秒降到约 0.1 秒，而且地图标签不会在缩放中途跳变——重新请求快照会让标签位置突变。

**时间轴与时钟严格一致**。每段视频时长按真实骑行时长等比分配，底部进度条每段宽度等于该段真实时长占比。早先的实现是每单平均分帧，却在底部画真实时间刻度，两者自相矛盾。

空档压缩到 1.2 秒并显示「等待 N 分钟」，而不是直接剪掉——观众看到时钟跳变和字幕，这天的形状才是诚实的。

每段至少 2 秒：一个 7 分钟的短途段挨着 86 分钟的长途段，按比例只有 0.6 秒，地名根本看不清。

**轨迹来源全程可见**。`load` 给每段标 `gps` 或 `inferred`，含推算路径的视频在底部标注免责声明。这不是可选的装饰——推算路径不是真实轨迹，画面必须说清楚。

**路径推算步行优先**。MapKit 没有骑行模式。默认驾车会把自行车导上京津塘高速并穿过两个收费站，所以优先用步行（走的是自行车实际会走的路网，也不受单行道限制），只有长途城际段找不到步行路线时才回落到驾车 + 避高速 + 避收费。`route.swift` 输出实际用了哪种模式，调用方按它标注，不能一律写成步行。

**子进程批量而非多线程**。`batch` 以 `python -m ridevideo` 起子进程，每个 worker 渲一整条视频。MapKit 快照和 ffmpeg 本身已是多线程，所以并行数取 2–5 而不是等于核数。进程隔离还让单条渲染失败不影响其他。

### 缓存策略

`src/ridevideo/cache/` 三份缓存都是跨次复用的：

| 缓存 | 失效方式 |
|---|---|
| `basemaps/` | key 里带 `PROJECTION_VERSION`，改投影逻辑时 +1 |
| `routes.json` | 按起终点坐标做 key，坐标不变就复用 |
| `locations.json` | 按坐标做 key |

底图缓存 key 带版本号这件事有实际原因：投影逻辑改过一次（v2 把 y 轴从 AppKit 的左下原点翻成 PIL 的左上原点），如果不让旧缓存失效，整条路线会南北镜像。

`bin/` 下的 Swift 二进制也是缓存性质的，首次运行编译，删掉会重编译。

## 路径解析

所有路径集中在两个 `paths.py`，起点是 `PROJECT_ROOT`，由模块位置向上推导而非按目录层数硬数——因为模块在不同深度（`cli.py` 和 `rides/load.py` 差一层）。

CLI 默认值也走这里。以前是 `Path("data/three-years")` 这样的裸相对路径，只在项目根目录执行才对。现在从任意目录都能跑。

两个环境变量可覆盖：`RIDE_DATA_DIR`（数据目录）和 `RIDE_FILTERS`（规则文件）。测试就靠前者跑在临时目录里，不碰真实数据。

## 数据与隐私

仓库里没有任何真实数据。`.gitignore` 排除 `/data/`、`input/`、`*.har`。

这不只是体积考虑：导出的 JSON 含真实订单号、车辆号和完整 GPS 轨迹，也就是三年的出行位置史。凭证只存在于 HAR 里，不会写进任何输出文件。

`examples/` 是完全合成的数据（坐标是编造的圆弧，订单号是 `SAMPLE0001`，带 `synthetic: true` 标记），让没有账号的人也能跑通渲染。

## 测试

122 个测试，分五组：

| 文件 | 覆盖 |
|---|---|
| `test_common.py` | 时长格式化、坐标解析、距离、读写 |
| `test_filters.py` | 筛选规则引擎、YAML 加载、默认行为等价性 |
| `test_api.py` | HAR 凭证提取，含「不该提取什么」 |
| `test_ridevideo.py` | 格式化、路径、缓存、时间轴排片 |
| `test_pipeline_contract.py` | 两包之间的数据契约、包独立性 |

测试用自建 fixture 而不是读真实数据目录，所以在全新克隆上也能跑。

几处测试是针对具体 bug 的回归：
- `duration_text(23810) == "6小时36分50秒"` —— 旧实现丢小时，把 119 分钟报成 `119分38秒`
- `_parse_coords` 跳过框架日志行 —— snapbin 的 stdout 会混入 `List has 3 nodes:` 这种，旧代码假定每行都是坐标，新数据首次渲染必崩
- `long-rides` 与退役的 `single-order` 模式逐值等价 —— 保证重构没改默认行为

## 已知的取舍与待讨论

这几处是我刻意留下的，值得一起看看：

**1. 两份 paths.py 和两份时长格式化**
包独立性的代价。有测试保证输出一致。替代方案是抽第三个共享包，但那会让三者绑定发布。

**2. `bulk.py` 的 main 还是长函数**
约 100 行，做的是「读缓存 → 筛选 → 抓详情 → 写六种产出」。可以拆成几个函数，但它是线性流程，拆开未必更清楚。

**3. 筛选规则不支持 or / not**
目前所有条件是「与」。真需要时可以加 `any_of:` 嵌套，但会让 YAML 复杂度上一个台阶。

**4. 详情抓取是串行的**
每笔一个请求，49 天约 400 笔。加并发会快，但接口限速未知，被封的代价比慢几分钟大。现在有 `--sleep-seconds` 控制节奏。

**5. ~~`groups` 和 `manifest` 的产出有重叠~~（已解决）**
两者都已删除。见下面「产出粒度：为什么是天」。

**6. 没有 CI**
有 pytest 和 ruff 配置但没有 GitHub Actions。加一个很简单，但渲染相关的测试依赖 macOS + swiftc，云端跑不了全部——需要区分哪些测试标记为仅本地。
